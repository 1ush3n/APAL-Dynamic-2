## 二、P2-1：把每一项优化目标、实际费用与报告严格对齐（最高优先级）

### 1. 问题在哪里

`utils/work3/objective_evaluator.py` 顶部文档仅列四种费用，但函数 `evaluate_trajectory_objective()`（约 173—201 行）实际还加了相邻正式修订费用 `j_revision`。`envs/work3/environment.py` 由 `_record_formal_revision()`、`_on_task_started()`、`_execute_synchronous_transfer()`分时结算相同类型的费用。`scripts/work3/evaluate_c_vs_d.py::evaluate_single_trajectory()`（约 725—737 行）把环境**已加权费用**赋给 `d_time`、`d_team` 等名称，又称其为 `raw_cost_components`；这与独立评价器同名的**未加权指标**含义不同。

设计稿 §6.3 曾给出带 `w_S D_station` 的**建议**目标式，但现行目标通过每次正式改站 `g(n)` 收费，没有独立的最终站位偏差训练权重。若直接叠加新 `w_S D_station`，就是改变算法目标，且可能重复惩罚同一次改站。本任务应明确写出现行可核算的最终式，并把最终站位偏差作为**单独报告指标**。若后续研究确需增加独立 `w_S`，必须另立方法变更和实验对照任务，不在此轮暗加。

### 2. 必须逐项表达的优化目标及代码对应

记 `N` 为一开始冻结的批次工序总数（例如小实例的总数；真实 283×10 批次为 2830），`H0` 为固定基准节拍；`P_q` 为实际全线同步转站时刻，`H_q=P_q-P_{q-1}`。在 `normalize_by_n=True` 的现行默认配置下，定义：

| 优化目的 | 指标/费用（实现与文本需要一致） | 发生及结算时机 |
|---|---|---|
| 保持**每次实际节拍**不过分超期 | `J_H=Σ_q [H_q−H0]_+/H0`；每次全线转站只计一次，不把五站分别相加，不用原绝对转站日历累计延误代替。 | 实际 `SYNCHRONOUS_TRANSFER` 事件结算 `w_h J_H` 的本周期增量。提前转站该项为零，周期内位置偏差另计。 |
| 让工序在**本周期内的开工位置**接近基准 | `b_i^0=S_i^0−P^0_{q_i^0−1}`，`b_i=S_i−P_{q_i−1}`，`D_T=(1/N)Σ_i |b_i−b_i^0|/H0`；提前和迟到同系数，实际周期整体平移不额外罚，后移任务仍沿用原偏移作软参照。 | 每道工序真实开工时仅结算一次 `w_t` 加权增量；预约时刻不算真实开工。 |
| 尽量保持**原团队成员** | `D_W=(1/N)Σ_i (1−|W_i∩W_i^0|/m_i)`；人数 `m_i` 是硬约束，比较具体成员而非人数。 | 真实开工时一次性结算 `w_w` 加权增量；换 1 人与换 3 人不同。 |
| 约束**实际正式改站次数**，尤其反复后移 | `G=Σ_i g(n_i)`，`g(n)=λ1 n+λ2[n−1]_+`，增量为 `g(n_new)−g(n_old)`；沿用当前实现：此项默认**不除以 N**，总费用为 `w_p G`。 | 只有正式目标站位变化时结算；首次即收费，后续加重。自然转站、同站换机、内部试算不增次；同一实际周期不能连续推到多个站。 |
| 约束**相邻正式版本的反复改动** | `R_T=(1/N)Σ_r |b_i^{r}−b_i^{r−1}|/H0`，仅在相邻两个已发布版本都有时间位置时计算；`R_W=(1/N)Σ_r (1−|W_i^r∩W_i^{r−1}|/m_i)`，仅双方团队均已确定时计算。 | 每次正式发布有变化时增量收费。后移仅记录目标站而团队尚未选定，不虚构一次全员替换；待目标站选队后再比较历史团队。`A→B→A` 的终局团队偏差可为零，但两次发布改动仍计两次。 |

**建议在方法文本及报告中采用与当前实现严格一致的主目标**：

`J_total = w_h J_H + w_t D_T + w_w D_W + w_p G + w_RT R_T + w_RW R_W`，其中 `w_RT`、`w_RW` 如未显式配置，则按现有 `ObjectiveWeights` 规则分别继承 `w_t`、`w_w`。`R_T/R_W` 已由现有 `j_revision` 汇总；`G` 已由 `j_postpone` 汇总，不在 `j_revision` 里二次收费。若 `normalize_by_n=False`，报表和方法必须显式记录此选项，不能把上述默认 `/N` 公式无条件套用于所有配置。`H0` 始终是固定基准，不能随上个周期延误重置。

**单独报告而暂不另收训练费用的指标：** 最终执行站位相对基准的改变数量/比例、累计后移次数及后移多次比例、整批完工时刻、各站/各架的传播轨迹、原始节拍超期小时量。最终站位偏差与过程改站次数不是同一指标；应让读者同时看到，但不得冒称已实现独立 `w_S D_station`。未来如决定新增该目标须另议权重与消融。

令 `A_n` 为累计**真实**加权费用，基础单步奖励 `r_n^actual=−(A_{n+1}−A_n)`；环境事件期间费用归当次 `step`。势函数塑形 `β(γΦ(s_{n+1})−Φ(s_n))` 属训练奖励增量，不加入 `J_total` 或生产绩效，不在中间转站把完整批次误当自然终止。不能再重复收逐步时间流逝、预测节拍差和终局同一超期费用。

## 三、P1-3：把工作三扰动暂定为“工序延迟开工”

### 1. 问题与设计依据

实验确认稿 §3.1 规定直接建模的是受扰飞机上某些工序的**开工可用性延迟**。用户本轮确定对外暂称 **“工序延迟开工”**，正式论文再讨论工程原因。不能凭空声称已建物料清单、共用物料传播、工装故障或真实供应链延误。现有 `environment.py` 内 `material_ready_time`、部分注释、`objective_evaluator`/评测脚本表述与场景说明可能使读者误以为实现了物料机制。

### 2. 精确定义，不更改物理逻辑

事件 `e=(τ,k*,A,R)`：在 `τ` 发生后才揭示直接受扰飞机 `k*`、目标工序集合 `A` 和恢复时刻 `R>τ`。对命中且**实际未开工**的工序，更新 `r_i ← max(r_i,R)`，真实开工 `S_i≥r_i`，同时仍须满足前驱、飞机位置、工人技能/日历和站位容量约束。已开工/已完成不撤回，未开工预约可以受扰并依法修订。`R` 是开工**下界**，不是把所有工序原计划开工时刻统一加上 `R−τ`，也不表示每项必然晚于基准相同小时数；后移不删除这一限制。`τ` 以前策略不可看到本事件真实内容，发生时可以知道准确 `R`。

### 3. 修改范围

1. 检索工作三对外可见的标题、docstring、README/任务表方法描述、场景 JSON 说明、评测 JSON 的 `disturbance_type` 与人读字段、图注/表头；统一使用“工序延迟开工（开工可用性延迟）”，英文暂用 `task start availability delay` 或 `delayed task start availability`。不要把工作二论文的已定“物料扰动”整体替换。
2. 内部 `material_ready_time` 若被广泛依赖，可以保留为兼容字段并加清楚注释；确需重命名时提供明确迁移、旧场景/检查点/schema 兼容与测试，不进行大规模纯改名重构。数值、事件优先级、掩码、奖励、场景种子、目标名单保持原样。
3. 把“受扰引起的延迟开工”与“所有其它原因造成的实际晚开工”区分清楚；报告预设目标数、实际命中数和未命中原因，不能把未实际命中的目标也计为受扰工序。

### 4. 验收

- 用 5 站、2 架小例：`τ=10,R=20`，某工序原计划 15；扰动发生前观测与候选不含事件内容，发生后未开工目标不得在 20 前真实开工；另一工序原计划 25 并不被机械改成 35；已开工工序保持到完工。已有同刻扰动/预约测试和后移保留限制测试不得回退。
- 对外交付的工作三说明与报告包含明确术语及定义；任何“物料”出现如属旧内部变量，不能作为实验已证实的原因宣称。静态检索列出保留例外，记录兼容依据。

### 1. 必须保持的四组定义

### 2. A 的可执行确定性规则（本地验证版本，记录为实施约定）

- 每个决策只用基准模板、当前已揭示事件和现场状态；已实际开工/完成硬冻结。所有任务保留原执行站位，**绝不使用 POSTPONE**。
- 在可合法**留站**预约的未开工任务中，优先基准站内计划开工位置较早者；并列依次按当前站位、飞机投产顺序、工序编号排序。此顺序只是 A 的确定性参照实现，不是 B/C/D 新增的人工优先级或硬先后约束；工艺前驱和并行仍由环境裁决。
- 优先使用基准团队；人员当前忙碌时保留该团队并由统一预约日历找未来合法时段，不能因为暂忙就认为技能不合法。只有基准团队不满足当前实际站位技能/人数/绑定等硬条件时，才从合法团队中按“更换人数最少 → 可行开工时刻最早 → 工人 ID 字典序”确定替代。使用既有 `duration_for_team` 和联合区间搜索，不能机械平移旧时刻制造资源重叠。
- 使用原站内偏移做二元对齐（若原目标已经过去，自然立即寻找最早可行时间）。没有可处理的新任务、仅有预约待执行时走显式/强制推进路径；不能用重复提交预约制造额外发布、更不能循环卡死。
- 若以上规则因无合法站内团队或真实物理矛盾不能完成，标记不可行/失败原因并保存轨迹，不能临时后移或借用未来事件信息。该规则作为 A 的正式定义草案提交到实验协议；如果代码数据表明需另外选择“并行工序的原顺序”口径，明确记录冲突实例和方案再定，不以吞异常假装可行。

### 3. B 的同网络动作约束

在 `Work3MethodProfile` 增加 B：图策略、`allow_postpone=False`、无时间辅助训练、启发式时间输入和启发式势函数；C 在相同图结构和物理仿真器下 `allow_postpone=True`。策略输入的站位分支掩码应在**快照生成或一个受控的不可变快照适配边界**将 B 的后移位置设为非法，然后同一已保存快照用于采样、联合 log-prob、PPO 重放和评测。不能只在环境末端拒绝已采到的 POSTPONE、不能只改评测不改训练，也不能让旧 log-prob 依赖改变后的现场掩码。保留留站、选队、二元对齐和显式推进行为。

正式 B 检查点应含 `profile=B`、图特征 v4、配置指纹等现有必需元数据；缺正式检查点时评测必须报错。**本地功能烟测**可显式标记随机初始化/调试模式，不能输出“B 优于 C”的正式结论。不要把 A 包装成 PPO 或错误加载图模型。
