## 一、贯穿全部任务的四条守则

1. **只有环境是物理真相。** worker 内的 `env.step()`负责合法性、事件、原始奖励和终止。主进程只根据**当时的**决策快照选择动作、计算价值与塑形；不能在主进程修改环境状态，也不能用当前环境重建过去 PPO 样本。继续将工序开工延迟作为扰动，不悄悄引入物料 BOM、虚拟规划层或名义节拍等待。
2. **三本账不能混用。** 分别记录 `environment_steps`（已确认完成的 `env.step()` 数，包含强制推进）、`rollout_segments`（采样段数）、`optimizer_steps`（PPO 和辅助损失的真实优化步数）。Lightning 的 `global_step` 可能随手动优化次数变化，不能代表环境步数或完整批次数。
3. **保留两套奖励字段。** 原始环境奖励 `r_raw` 与独立费用账本逐步对齐；塑形奖励另记 `r_shape = γΦ_{version}(s')−Φ_{version}(s)`，策略训练奖励为二者之和。实际自然/失败终止时的终止势按已确认规则处理；可继续的段末和预算截断不能被误作自然终止。不要拿塑形后的回报比较 C/D 的真实生产成本。
4. **每项只验证它引入的风险。** 先写最小反例，确认失败原因，再改实现、跑定向及相邻回归、提交可运行版本。不要在任务 2–6 顺手开启 AMP 或改正式训练预算；完整工作三测试在运行时链路完成后统一再跑。

## 二、任务 2：决策快照与条件选队

**关键风险：** `@dataclass(frozen=True)`只冻结属性绑定，不冻结内含 `Tensor`、`HeteroData`、列表或字典。仅执行 `tensor.cpu()` 也可能仍共享 CPU 底层存储；须在形成消息前逐字段复制/转换成自有 CPU 数据，并验证改变原环境、原张量及之后的图缓存不会改变已发快照。完整的图和人员日历逐步复制可能很耗 RAM；先保正确性，再记录单快照大小、序列化耗时及每段留存量，不为省内存而恢复引用别名。

- 除候选任务及首层站位掩码，快照须携带**选了若干工人之后**计算合法补全所需的规则输入：有序工人稳定 ID、技能、要求人数、合法团队规则和适用的工人绑定信息。不能仅传首步工人布尔掩码，也不宜枚举可能指数增长的所有团队。
- 将现有 `valid_team_completion_workers()`依赖的纯规则提取成可对快照执行的同一函数；旧环境入口只包装同一函数。环境仍在动作执行时基于实际状态二次校验。团队成员的身份和指针**顺序**在 PPO 样本里保留，计算团队变更比例时才按成员集合比较。
- 图中 `(aircraft_id, task_id)` 到 task 节点和站内 worker ID 到 worker 节点的映射必须随快照保存。候选索引的稳定顺序、每步已选工人及布尔掩码也进入 `sample_record`；后移与强制推进分支不生成选队/对齐头的虚假概率。
- 快照只能包含当前实际已揭示的扰动信息。构造两份 τ 之前物理状态相同、未来扰动不同的场景，其图、候选、时间输入及 mask 应一致；τ 后才可分别变化。

**验收反例：** 技能约束使四人中只有两人可组成两人团队；逐个已选前缀核对快照规则和环境规则输出完全一致。采样后修改环境技能/日历/基线团队边，旧快照的概率重放不变；伪造不合法团队交给 `env.step()` 必须被拒绝。

## 三、任务 3：单环境 FP32 对照

**关键风险：** 一次性比较“最终成功”会漏掉事件时刻、费用及预约修订的细微差异。用同一基线、同一场景和**同一冻结动作序列**，逐步对比旧直接环境路径与 `num_envs=1` 的 spawn 路径；此时不让策略分别采样随机动作。

- 每步比较仿真时钟、当前飞机站位、预约/开工/完工状态、有效事件次序、实际进线/转站、`r_raw`、费用分项、`terminated/truncated`、`success/reason`。浮点比较用原有数值契约的容差，不对语义字段放宽比较。
- 既要覆盖无扰动，也要覆盖**实际命中的**工序延迟、同刻扰动/开工、合法后移、预约修订、`ADVANCE_TO_NEXT_EVENT`和已开工硬冻结。前一个动作将内部事件推进到下一决策点时，只把这一整次 `env.step()`计为一次动作。
- `spawn`的 worker 函数应位于可导入模块顶层；Windows 的入口要受 `if __name__ == "__main__"`保护。worker 只通过定义好的命令/响应收发 CPU 数据；响应附 `(worker_id, episode_id, request_id)`，发现过期或错配消息立即失败并清理，不能套用到另一轨迹。
- worker 创建与关闭必须有确定的生命周期：正常结束、异常、超时、键盘中断都回收子进程；不要靠进程守护线程静默退出。worker 内不要初始化 CUDA 或复制 Actor。

**门槛：** 逐步对照无无法解释的偏差、独立轨迹检查一致，单 worker 关闭后没有遗留进程，才能开始任务 4。

## 四、任务 4：双环境、预算及超时

**预算规则建议直接写为不变量：**

```python
remaining = max_environment_steps - acknowledged_steps - in_flight_requests
dispatch_count = min(remaining, number_of_active_envs)
```

派发前先预留额度；响应完成时将其从 `in_flight_requests` 转为 `acknowledged_steps`。最后一轮只向稳定排序的前 `dispatch_count` 个活动环境派发，不能先给两个 worker 都派发，再把超过预算的结果从日志删除。一个显式/强制 `ADVANCE_TO_NEXT_EVENT` 与普通合法动作均占一个额度；事件队列内部跳时不单独占额度。

- **超时需分清提交与确认。** worker 可能已经执行 `step()`但响应丢失。这时无法证明真实执行总数恰等于已确认数。日志同时保存 `dispatched`、`acknowledged`、`in_flight/unknown`；该 episode 标为基础设施中断，不把丢失转移计入 PPO、不从缺失后继观测 bootstrap，也不在同一环境上盲目重试可能重复生效的动作。
- 固定场景映射 `(worker_id, episode_index)`确保运行可复现；不同策略可能在相同聚合预算内实际启动了不同数量的 episode，因此“事件清单相同”不代表“实际经历的事件相同”。训练报告逐项记录计划、开始、触发、实际命中与未命中原因；正式配对评测另须逐条遍历固定事件集。
- 同步向量轮次允许活动 worker 数变化：完成/失败后是否启动下一 episode 取决于剩余预算和已固定的停止规则；只重置已结束的 worker，不重置其他在制轨迹。快的 worker 不可以私自越过轮次使用更新后的 Actor。
- worker 异常必须包含原异常、命令和 worker/episode/request 标识；主进程收到后停止采样、处理已确认响应并有界关闭其他 worker。不要静默重启继续该 episode。

**验收反例：** 两环境总额度 5，固定派发顺序，恰好有 5 个已确认 `env.step()`；第 6 个绝不被派发。另测 worker 返回慢、响应缺失和进程异常：只记录已确认转移，运行结果不能误报自然结束。

## 五、任务 5：GAE、标签、预测器版本

- `episode_id`若在各 worker 内从 0 重复计数，所有缓冲键必须含 `worker_id`。`segment_id`用于标记本次 rollout 边界；先对每个 `(worker, episode, segment)` 的时间顺序计算优势，再合并样本做 PPO mini-batch。段末 `V(s_end)`应以**采集该段时的策略/价值版本**在更新前计算；不可从重置后的新 episode 取价值，也不能在 Actor 更新后回填旧段价值。
- 自然成功及不可恢复失败的该 episode 真正终止，不向下一个 reset 状态 bootstrap；仅采样段结束或仍有合法后继状态的预算截断按已确认口径 bootstrap。墙钟在途丢失没有完整转移，也没有可用 `s'`，不能构造一个零奖励尾步凑 GAE。
- 时间头训练标签按 `(worker, episode, cycle, decision_id)`缓存**当时**图和启发式预测，跨段保留。同一实际脉动可为该周期多个决策补各自残差；未发生脉动则标签缺失。合并辅助样本时别让较长周期天然拥有更多权重而未经记录；记录每周期样本数和监督更新次数。
- 每条 episode 持有冻结的 `(predictor_version, snapshot)`。环境 A 结束后可形成新版本供**新 episode**使用；仍在运行的 B 保留旧版本，即使共享图编码器/时间头已经优化。只有版本引用数归零才清理旧副本；潜在的旧版本存储量和内存峰值需要记录。
- 势函数从冻结版本计算 `Φ(s), Φ(s')`，并保存原始奖励、塑形量、预测版本及所用时刻。检查 episode 内版本全相同；用独立费用账本核对 `−Σr_raw`，不能以 `−Σr_train`核对原始成本。

**验收反例：** 环境 0 已完成并刷新版本 1，环境 1 正在周期内继续且仍使用版本 0；环境 0 新 episode 使用版本 1。三条轨迹的标签、GAE、塑形值互不串联。

## 六、任务 6：Lightning 手动优化，先 FP32

- 在 `training_step`里按顺序明确：**用当前权重采集固定段 → 给每条段求更新前 bootstrap 与 GAE → 锁定 PPO 样本 → 多轮 mini-batch 反传与更新 → 对已就绪时间标签作受控辅助更新 → 写日志**。不能在采样与这轮 GAE/bootstrap 完成之间优化 Actor/Critic。Lightning `global_step` 不能替代交互预算；DataModule 的请求只是触发一次采样段，不应由 DataLoader worker 持有环境或 Actor。
- `self.automatic_optimization = False`；`configure_optimizers()`对 Actor、Critic、时间头、共享图参数去重后创建**一个优化器所有权**（可按参数组设置不同学习率），`PPOTrainerWork3`只返回损失及诊断，不创建优化器也不执行 `.backward()`、`.step()`。如果仍需旧训练入口兼容，明确隔离旧的优化器入口，禁止新运行时同时实例化两套优化器。
- 用 `opt = self.optimizers()`、`opt.zero_grad()`、`self.manual_backward(loss)`、Lightning 支持的梯度裁剪、`opt.step()`；训练步骤中核验损失和梯度为有限值。手动优化下不能以 `Trainer(gradient_clip_val=...)`参数代替训练步骤中显式的裁剪。具体 API 需以 `rag_env` 所装 Lightning 版本和[手动优化官方说明](https://lightning.ai/docs/pytorch/stable/common/optimization.html)核对。
- 确保 rollout 采样与 PPO 更新使用的是 LightningModule**同一个** Actor 对象。不要在协调器中拷贝一份 Actor 后更新另一个；记录每段的 `policy_version`，样本重放对应采样时的掩码、图和显式时间输入。
- DataLoader `num_workers=0`，若使用可迭代的 rollout 请求，其生产应随训练步骤推进，不预先缓存旧 PPO 样本；显式指定 Trainer 的停止条件与运行时聚合交互/墙钟上限之间的映射。worker 池在 Trainer 生命周期里安全创建/关闭，异常时同样关闭。

**门槛：** CPU FP32 的 Lightning 实际完成一次 PPO 更新且共享图参数有梯度；日志中优化步数、辅助更新次数和环境步数三者分别正确；旧定向 PPO 回归无退化。

## 七、任务 7：AMP 与检查点

- **先 FP32 对照，再 BF16/FP16。** 同一配置下采样前向和 PPO 重放前向使用相同 autocast dtype/设备及同一套 FP32 logits、mask 和概率计算契约。`Categorical`及重要性比率涉及的 logits/log-prob、GAE/优势、value 目标、费用账本应在 FP32 中处理，并逐项检查有限性。AMP 路径与 FP32 路径动作可能因舍入不同，不要求它们逐步选中同一动作；要求**各路径内部**采样/重放一致。
- 只对一次 Actor/Critic/图/时间头前向和可安全混合精度的算子启用 autocast。工人/站位合法掩码、人员 ID、时间比较、事件队列、费用分项都在 CPU 的既定数值语义下运行。BF16是否可用以目标机 `torch.cuda.is_bf16_supported()`及实际一段更新为准；不支持则明确失败并经配置选择其他精度。
- 手动优化的 FP16 缩放/梯度裁剪交给 Lightning 精度插件，不再新增第二个 `GradScaler`，且不要绕开 LightningOptimizer 直接调用底层 `.step()`。[PyTorch AMP 官方示例](https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html)指出，对缩放后梯度检查或裁剪前必须先解除缩放；具体处理在插件的实际版本中通过对应 Lightning 接口核实。
- `C`可不含时间头，但检查点须明确 profile；`D`必须包含**经过训练且版本匹配**的时间头、归一化信息、图特征版本及塑形版本，不能从 C 或旧无图权重静默凑参数。模型/评测权重与可恢复训练状态分开标记；没保存 worker 环境状态、滚动段、缓存和 RNG 时明确 `resume_capability=non_exact`。
- 在完整图状态下同时测 CPU 主机内存、GPU 峰值显存、每步图快照大小、序列化耗时及单/双环境吞吐；不能只看 BF16 的显存下降就声称加速。限定在实际测试的 RTX 4060、batch、rollout、`num_envs`和 dtype 组合说明结论。

**门槛：** 使用真 CUDA 的配置完成一次 AMP 采样及更新，采样/重放误差在事先记录的容差内，无 NaN/Inf；完整 D 推理检查点能够严格加载，旧/随机 D 明确拒绝；C checkpoint 可按其 profile 严格加载。
