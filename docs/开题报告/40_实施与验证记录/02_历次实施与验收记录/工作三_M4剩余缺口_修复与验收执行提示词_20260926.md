## M4-G1〔确认存在；正式采集前优先〕：M4 数值与标签一致性门禁

### 1. 问题是什么

`scripts/work3/train_time_predictor.py::load_official_trajectory_splits()` 已拒绝不完整、不成功、不可行或标签为 `None` 的轨迹，但只验证标签“存在”。它没有验证 `h0`、`current_time`、`estimated_cmax`、`actual_transfer_time`、`label_y` 和 32 维 `state_feat` 的数值有限性，也没有按

\[
y_n=(P^{actual}_{q(n)}-\widehat P^h_{q(n)}(s_n))/H_0
\]

重新核对标签。现有 `models/work3/train_time_head.py::StepResidualDataset` 会把这些字段转换成浮点数；如落盘产物含 `NaN`、`Inf` 或错标而仍带 `label_available=True`，后续训练可能接收损坏数据。采集端目前用真实转站时间计算标签，问题位于**正式落盘产物的验证边界**；不要据此声称采集算法已经算错。

### 2. 如何修改，注意什么

1. 为官方轨迹建立一个**共用的逐轨迹、逐步骤校验函数**；在 `load_official_trajectory_splits()` 完成清单覆盖检查后、调用训练器前执行。若复用到 `StepResidualDataset`，保留其历史调试输入契约，不能让正式路径悄悄跳过坏样本。
2. 校验 `h0` 为有限正数；`total_tasks` 为正整数、`completed_tasks == total_tasks`；每条 `state_feat` 能转为**恰好 32 维**浮点向量且元素全部有限；上述各时间与标签均有限。为兼容现有测试的 `torch.Tensor` 和列表输入，使用显式转换及形状检查；不要无意把字符串、布尔值和非数值当作合法标量。
3. 核对 `actual_transfer_time >= current_time - tol_time`；`cycle_idx` 为有效正整数；`label_y` 与上述公式在明确的绝对/相对容差内一致。容差应容纳正常 `float32` 序列化误差，远小于一次有意义的时间误差；记录所选单位和容差，不把容差增大到足以掩盖错周期。
4. **优选增加独立的真实转站对应关系校验。** 当前采集返回 `transfer_count`，没有把完整 `transfer_history` 随轨迹保存。可在采集结果中加只读 `transfer_history`（由 `env.state.transfer_history` 复制），正式加载时检查每步 `cycle_idx` 在范围内，并且该步 `actual_transfer_time` 与 `transfer_history[cycle_idx-1]` 一致。同步更新官方产物的测试夹具。若旧调试产物无此字段，允许标注为“历史/非官方”，但**正式 M4 路径必须提供**；不能把 `transfer_count` 伪造为时间序列。注意统一暖机后的周期索引仍以整个真实环境的转站序列解释。
5. 错误信息应包含划分、`scenario_id`、`step_idx`（如存在）和失败字段；禁止在失败时只打印 NOTICE 然后继续训练。不得从标签反向修正轨迹以“自动修复”真实生产记录。

### 3. 需要补充的专项测试

在 `tests/work3/test_time_head_training.py` 中复用官方 train/validation/test 临时清单夹具，每个反例只变更一个字段，调用真实 `load_official_trajectory_splits()`：

- 正常的有效多周期轨迹可加载；两个周期的真实转站时刻不同，标签逐步可复算，暖机已发生的转站编号不被重新归零。
- 分别注入 `label_y=float('nan')`、`estimated_cmax=float('inf')`、`current_time=float('nan')`、`state_feat` 某维 `Inf`、`h0=0` 或 `NaN`；各自必须在拟合前拒绝。
- 保持全部字段有限但把正确 `label_y` 加 `0.1`；必须拒绝。保持 `label_y` 自洽却把该步 `actual_transfer_time` 改为另一周期的转站时刻；若实施了第 4 项，也必须拒绝。
- 将 `state_feat` 变为 31/33 维或非数值内容；拒绝并指出场景和步。有效 `torch.Tensor(32)` 与 32 维列表正常通过。
- `total_tasks=completed_tasks=0` 不应因两个计数相等被认作完成。训练清单与测试清单交叉、缺少真实标签等现有门禁继续生效。

先在基线提交上运行至少一个错标/非有限反例，记录**预期的红灯**；若它已红，证明此前确有缺口。测试不要只直接调用新校验助手，要经过正式加载入口。

### 4. 验收标准

- 上述异常在时间头实例化或优化器更新前明确失败；正常真实完整轨迹及官方测试夹具通过。
- `label_y` 与真实转站历史、同一步启发式值和 `H0` 一致，不能凭一个自称 `label_available=True` 的布尔位通过。
- `test_time_head_training.py`、`test_trajectory_collection.py` 与受影响的时间头回归均通过；无新 skip；现有“正式产物全部缺失时 skip、部分存在时失败”规则保留。

## M4-G2〔确认存在的适配器盲点；其余覆盖先核验〕：独立执行轨迹复核

### 1. 问题是什么

`utils/work3/trajectory_feasibility.py::validate_trajectory()` 的位置检查要求 `aircraft_station_at_start == station_id`，但 `check_environment_trajectory_feasibility()` 构造执行记录时把**两者都直接设置为 `task.current_station`**。因此 M4 采集调用这一路径时，这一项相等性检查恒为真。它仍检查飞机站位的进/出时间，不能因此断言整个可行性检查失效；但不能称该“站位相等性”已经独立验证。

`training/work3_vector_env.py::_execution_record()` 已有 `start_station_by_task` 的开工时现场位置记录，说明仓库另一路径有更可靠的信息来源。另请核查独立检查器目前只核对团队人数、技能、资源区间等，并未重算团队效率所决定的实际加工时长。**这项属于待反例确认的覆盖差异**，不能未经模型源数据核对就宣称真实轨迹存在时长错误。

### 2. 如何修改，注意什么

1. 为 M4 采集路径提供来自真实 `TASK_START` 事件的飞机站位快照，而非由任务目标站位反填。优先复用现有开工事件回调/审计记录方案；若需新增 `TaskRuntimeState.actual_start_station`，只在成功物理开工的一刻赋值，此后视作执行事实，不随预约改动或飞机自然转站重写。同步审查 `copy/reset` 与向量 worker 审计序列化。不要以基准站位或当前结束时位置代替开工位置。
2. `check_environment_trajectory_feasibility()` 构造记录时应读取该独立字段；完整轨迹若缺少开工时站位事实，明确报告 `missing_actual_start_station`，不能自动回退到 `current_station`。继续保留从飞机进出站历史取得的 `station_entry_time`/ `station_exit_time`，避免削弱现有跨脉动加工检查。
3. 将标准团队工时的**静态输入**（任务标准工时、需求人数、团队成员效率）与实际 `end-start` 对照。先核对 `environment.py::duration_for_team()` 当前是否仅由这些量和协同系数决定，以及零工时/虚拟节点是否进入工作三实体集。若可以独立复算，以公认公式和固定数值容差新增 `duration_mismatch`；不能简单用 `task.execution_duration` 和实际时长互比，因为两者可能出自同一次错误排程。若静态输入不完整，单列“未覆盖团队工时”，不要凑一个看似独立的等式。
4. 关于“所有合法站位”的声称，先阅读 `ConstraintEngine.station_violation()` 的真实规则和源数据。现有独立检查至少覆盖固定站位、上界和已执行前驱的站位单调性；若仍有独立可读取的其他静态站位限制，补入 `TaskConstraintRecord` 并逐项校验。若只是这些规则的另一种表达，不新增冗余字段或与环境掩码互相调用的循环依赖。
5. 不能把独立检查写成调用 `env.validate_postpone()`、`env.duration_for_team()` 后直接照搬布尔结果；检查路径要可用**固定、可审计的执行日志和静态参数**独立运行。若采用共享纯数学函数，注明共享的是公式而非环境运行状态，并通过人工可核对的数值例测试。

### 3. 需要补充的专项测试

在 `tests/work3/test_work3_f04_trajectory_checker.py` 中先添加最小反例：

- 完整的合法小轨迹中，目标执行站为 1，但真实开工时飞机仍位于站 0；进出站时间可以人为给出对目标站看似合理的数值，使原有时间比较不先报错。经过**M4 实际使用的适配器**后必须得到 `aircraft_position`。不能仅直接构造 `TrajectoryExecutionRecord(aircraft_station_at_start=0)` 测 `validate_trajectory()`，因为已有测试覆盖这个较浅层逻辑。
- 一项实际开工记录缺少开工站位，M4 适配器返回明确错误；不能变成可行轨迹。合法完成轨迹通过，飞机后来同步转站不改变保存的开工站位。
- 保留现有“工序执行跨越同步转站”反例；确保新字段没有绕过 `processing_across_transfer`。
- 如果第 3 项可以独立复算：构造标准工时、人数、效率明确的手算例，合法时长通过；同一团队时长被短报或长报时分别报 `duration_mismatch`。对浮点容差内的正常舍入不误报。
- 如果第 4 项发现额外独立站位限制，针对那条**真实存在**的限制各加一个负例和一个合法边界例；不要凭想象造一个实际实例不具备的“任意站位白名单”。

同时调用正式 M4 采集与正式评测的检查入口，核对同一执行日志得到一致违规分项；若两个入口用不同审计对象，先解释字段来源和一致性规则。

### 4. 验收标准

- 开工站位来自实际物理事件；任务目标站位独立存储，人工注入的两者不一致被拒绝。
- 已有技能、前驱、同一工人重叠、容量、到达时间和跨转站区间回归不退化；完整真实轨迹的检查结果仍可复现。
- 工时与其他站位条件的检查范围有明确结果：**新增可靠的独立检查并通过反例**，或在任务记录中明确说明静态数据不足/语义等价及不扩展的理由，不以“全部物理约束已覆盖”替代证据。

## M4-G3〔口径与后续阶段门槛；不能靠改一个文件“修完”〕：离线 M4 与正式方法 D

### 1. 问题是什么

当前 `collect_validation_trajectories.py` 使用 `HeuristicAgentWork3` 收集样本和 32 维紧凑状态特征；`train_time_predictor.py` 的离线时间头输入维数固定为 32。`models/work3/train_time_head.py` 保存的 M4 检查点是该**离线可学习性验证**的产物。确认设计中的正式 D 使用 Actor 的共享图表征、在线时间辅助训练、修正时间进入动作上下文及冻结势函数；正式评测也要求匹配的 D 检查点。二者研究角色不同。当前缺正式 D 检查点的两个测试与缺官方 M4 产物的一个测试仍为 skip。

### 2. 如何处理，注意什么

1. 不把离线 32 维 M4 检查点直接加载成正式图策略 D 的时间头，也不因 M4 达到 15% 验证改善就宣称 C/D 调度改进。保留 `signed_residual_v1` 名称时也要同时校验输入维度、图特征版本、训练来源及方法 profile。
2. 检查现有文档、CLI 输出、日志中“基线 C”“M4 PASS”“方法 D 已训练”等措辞；当轨迹来自 `HeuristicAgentWork3` 时称“固定启发式采样策略的 M4 离线验证”，不要冒称已训练正式 C 图策略。只做必要文案与元数据澄清，不为改名称重写算法。
3. 正式 M4 的 25/10 轨迹、服务器条件、离线验证和正式 D 训练属于**下一阶段真实实验**；本任务只把入口门禁补齐。三项 skip 保持诚实：产物缺失时允许既定 skip，部分生成时必须失败；绝不删除或改成无条件 pass。

### 3. 需要补充的测试

- 核对已有正式 D 检查点契约测试：把 `in_dim=32` 的 M4 离线权重包装成 D 检查点时应明确拒绝；旧版或随机 D 权重也不能作为正式评测通过。
- 如缺少该专项反例，可加一项最小检查点兼容性测试；若已有等价覆盖，记录测试节点即可，不写重复镜像测试。
- M4 三产物全缺可跳过、仅生成其中一项必须失败、三项齐全须在官方验证轨迹上重新计算阈值，现有测试应继续成立。

### 4. 验收标准

交付说明明确区分“入口安全已通过”“离线 M4 尚未运行/或通过”“正式 D 闭环训练尚未运行/或通过”；`1301 passed, 3 skipped` 不得写成 `1304 passed` 或“全部设计验收”。
