## 1. align 的真实语义

`align` 是执行分支的**对齐选项**，不是独立动作：`ActionBranch.STATION_EXECUTE`（留站执行）带 `align∈{0,1}`，`ADVANCE_TO_NEXT_EVENT` 与 `POSTPONE` 没有该字段。

`envs/work3/environment.py::AirLineEnvWork3.step` 中，`align == 1` 会把开工搜索下界抬高到 `last_transfer_time + task.in_station_offset`（基准站内偏移对应的名义时刻）：

```python
if align == 1:
    align_target = self.state.last_transfer_time + task.in_station_offset
    search_start = max(search_start, align_target)
```

`align = 0` 只用最早可行安排（`max(当前时刻, 物料下界, 前序释放)`）。因此 **align=1 只是加了一条下界，并不强制改变开工时刻**：若该下界本来就已经不紧（任务自然排在偏移之后），align=0/1 得到的实际开工时间相同。所以本轮把两类都记：标签被改写的次数，与实际生效（下界起作用）的次数。

另外，`align` 不进入任何费用项：`J_revision` 比较的是发布后的 `position = scheduled_start - last_transfer_time` 与团队，而不是 align 标志位。因此干预只能通过改变实际开工/团队来间接影响费用。

**与上一轮的关系（先校正结论）**：上一轮的 0% 对齐准确率是**教师状态、教师前缀条件下**的单头指标，不能扩写为“原 C 在所有自主访问状态上从未选过 align=1”；也不能据此说对齐头是全部费用差距的唯一原因——原 C 在教师状态上的决策类型、工序、团队也都不同，且 BC 更新了共享编码器与多个策略头。本轮只测“把 align 改成 1 的闭环效果”。
